# Session Note Schema (hippocampus = fast episodic capture)

> Tree & naming → [[vault-tree]]

## Frontmatter
- `uid` — unique id (`PROJECT_PREFIX-YYYYMMDD-HHMMSS`).
- `project` — project slug. **Never parsed from the uid prefix** — recall and `ss` grep `^project:` directly.
- `git_branch` — working branch (empty for non-code sessions)
- `git_worktree` — working worktree (empty for non-code sessions)
- `created`
- `updated`
- `status` — `active` | `done` | `cancel` — **hard rule: these 3 values are all there is. No extensions**
- `session_type` — (optional) marks special sessions such as `dreaming`. Absent = a normal work session.
- `result` — **dreaming reports only; a separate axis orthogonal to `status`**: `success` | `partial` | `failed`. For dreaming, "is it finished" (`status: done`) and "did it go well" (`result:`) are different questions, so the axes are split. That is, a dreaming report = `status: done` + `result: success|partial|failed` + `session_type: dreaming`. **Never used on normal sessions.**
- `writer` — the actual (human) user (exception: dreaming reports use `writer: scribe`)
- `cc_session_ids` — [CC session ids that touched this file; prepend on every resume]
- `related_ticket` — when linked to an external ticket
- `tags` — []

> ⚠️ **The `status:` vocabulary differs per object kind — never mix them.** The same key name uses different value sets in three places. Grep one side with the other's vocabulary and you silently get 0 hits.
>
> | Object | Value set | Canon |
> |---|---|---|
> | **Session note** (`sessions/<uid>.md`) | `active` \| `done` \| `cancel` | this document |
> | **Docs document** (PRD·FRD·TDC·POL·ADR…) | `stub` \| `draft` \| `approved` \| `deprecated` | [[project-docs-convention]] §frontmatter Standard |
> | **Knowledge note** | `fresh` \| `stale?` | [[knowledge-convention]] |

## Sections
- `## Goal` — this session's goal (minimum achievable unit)
- `## Context` — why this goal. **★ recall is injected here**: at session start, pull in related Knowledge and past Mistakes
- `## To-Do-List` — **lightweight resume actions** (open items the next session reads — chores that never became cards, resume memos, unresolved verification items). What the canonical work queue is: **canon = the PM role document** (the `CLAUDE.local.md` generated by `/brain:init`) — linked via session frontmatter `related_ticket`. **Never duplicate the task status graph in session notes**
- `## Progress` — by date, newest on top
  - `### YYYY-MM-DD` — date heading. An optional **status suffix** may follow (`(parked)` / `(completed)`); see [§Progress entry status suffix](#progress-entry-status-suffix-statusline-contract) below. The suffix is **parsed by the statusline**, so the notation is a contract.
    - `#### Done` — completed
    - `#### Mistake` — mistakes  ← highest reuse value (prevents repeating the same mistake). Also used as a salience signal.
    - `#### Fixed` — how the mistake was fixed
    - `#### Learned` — things learned (write atomically → input to promotion)
    - `#### Outputs` — outputs (paths/content), documents created under docs, code file names, etc.

### Progress entry status suffix (statusline contract)

The **newest** `### YYYY-MM-DD` entry's suffix is read by the statusline to tell a session's live state. The notation became a contract the moment a parser depended on it — treat it as one, not as free-text decoration. The suffix carries **exactly one status token**.

- **Vocabulary — closed set** (this table is the whole vocabulary; do not extend it ad-hoc):

  | Suffix | Meaning | Emitted by |
  |---|---|---|
  | *(none)* | in progress — active work | `ss` (first entry) |
  | `(parked)` | suspended / handed off | `sh` |
  | `(completed)` | closed (`done` or `cancel`) | `sc` |

- **One status token only.** A round-count or short qualifier may trail the token — `### 2026-07-22 (parked #5)` — but the token itself stays one of the set above.
- **Never a non-status description in the suffix.** `(device smoke-test)`, `(waiting on review)` and the like are **forbidden** here — they go on the `**Stopped at:**` / `**Final state:**` line or in the body. The suffix answers only *what state*, never *why* or *what next*.
- **Vocabulary cap — under 5 tokens, hard.** The `status:` 3-value hard rule (`active|done|cancel`) survives *because* the set is tiny; the same logic governs this suffix. Growing the vocabulary is a canon change (edit this table), never an ad-hoc call at write time. If a new token seems needed, it almost certainly belongs in the body instead.
- **Parser defence — unknown suffix falls back to `active`.** The statusline recognises `parked` as its one meaningful token; any suffix it does not recognise (including a malformed or future one) is read as `active` (in progress). A visibly-wrong "active" is preferable to silently mis-reporting state. This fallback is a safety net, **not** licence to invent suffixes — an unrecognised token still violates the closed set above.
