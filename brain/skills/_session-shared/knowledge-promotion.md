# Reference: Knowledge Promotion (shared procedure)

> The **Knowledge Promotion** procedure shared by `sh` and `sc`. The **PM (main session)** running the calling skill reads this document with Read and performs it as written. Not executed standalone.
> **Executor = PM** — reads, detects, and judges only; **all vault writes are delegated to the scribe worker** (see "Write boundary" below).
> Canonical note schema: `docs/knowledge-convention.md` · canonical promotion topology: `docs/knowledge-escalate-convention.md`.
> **What this document is canonical for**: the two-gate judgment — score gate (sum ≥ 3) + the similar-note verdict enum (`promote / already_known / not_durable / unsupported`, closed — never extended) · the reject-log format (canonical map in `README.md`).

## Why separate

Session Progress is the **time axis** — for continuing this work right now. knowledge is the **topic axis** — needed again in other work. The intuition for sorting Learned items:

> Will this content be needed again three months from now in completely different work?

Intuition is only framing — **the gate is decided by score** (subjective → quantitative):

| Axis | Range | Meaning |
|---|---|---|
| **Reusability** | 0–2 | 0=this task only · 1=recurs in this project · 2=multiple tasks/projects |
| **Failure-prevention value** | 0–2 | 0=none · 1=prevents time waste/gotchas · 2=repeated mistakes/data loss/security (Mistake bonus) |
| **Source confidence** | 0–1 | 0=guess/unverified · 1=execution-verified/backed by docs |

- **Sum ≥ 3 → Gate-2 candidate** (promoted unless the similar-note verdict rejects it — Steps below). A verified repeated mistake (0+2+1) and something reused and verified (2+0+1) both pass.
- **Sum < 3 → reject-log** (no promotion; Step below), reason code `not_durable` — unless the item carries **cross-project value**, in which case it parks as a **full note in `<vault-root>/candidates/`** (the promotion-candidate pool; Steps below). Speculative one-offs go to the log. **Record instead of discarding** — audit + Dreaming recurrence signal.

## Write boundary — all vault writes go to scribe (important)

> **PM = read, detect, judge only. Every write of vault content is delegated to the scribe worker. The calling skill hands over a recording brief — what, to which path, with what content.** (Canonical governance: `docs/memory-control-convention.md` §Governance)

- **Vault writes = all through scribe, the single scribe**: knowledge notes · `_index.md` (folder TOC) · `0.rejected.md` · **plus session Progress · park/closing entries · frontmatter · To-Do-List — all of it**. (The sole exception = `git add`·`git commit` — a commit is boundary recording, not content authorship, so it is the PM's job; `docs/versioning-convention.md`.)
- **The PM (executor of this procedure) does judgment only**: selects promotion candidates · decides what gets recorded where → hands that decision over as a **scribe recording brief**. (The two-gate judgment is **applied** by scribe exactly per the Steps below — the judgment logic itself is unchanged.)
- That is, in this procedure the PM (a) **delegates** the `Learned` items to scribe, (b) scribe auto-selects and promotes via the two-gate judgment, and (c) inserting the returned backlinks into the session's Learned is **also delegated to scribe**. The PM writes no vault files directly, **and asks for no approval** (sole exception: the `common/policies/` signature batch — Step 4).
- **Delegation runs through the `Agent` tool**: spawn recording (scribe) briefs with `subagent_type: worker` (depending on the plugin install form, `brain:worker` — verify after install and update this line). Code implementation briefs go to `coder`; verification/review to `verifier`.

> ⚠ **Do not split the boundary on the grounds that "it is more efficient for the calling skill (PM) to write session Progress directly"** — the moment there are two scribes, the same file gets silently clobbered. Same-machine concurrency has no locks; **the single scribe plus the PM's overlap arbitration is the only defense** (`docs/memory-control-convention.md` §Governance · `docs/versioning-convention.md`).

## Steps

1. **Automatic promotion (no approval gate) — two-gate judgment** — **delegate** this conversation's `Learned` to scribe; scribe judges every item through the two gates below and **auto-promotes only what ends `promote`**. **No AskUserQuestion — no user approval is requested.**
   - **Gate 1 — score gate (deterministic, unchanged)**: the **score gate ("Why separate" above, sum ≥ 3)**. **Below-bar items (< 3) are not discarded** — one with **cross-project value** goes as a **full note to `<vault-root>/candidates/`** (the note is its own record — no reject-log line; destination note below); **the rest get one line to `<project>/knowledge/0.rejected.md`** (audit + Dreaming recurrence signal), reason code always `not_durable` — the line's score triple is the actual Gate-1 rationale; the fixed code only keeps the line format uniform, and `sum < 3` on the line marks it as a Gate-1 reject.
   - **Gate 2 — similar-note verdict (Gate-1 passers only)**: check each passing item against the **existing-note title list the brief already carries** (Step 2 glossary anchoring — recall's grep-priming title enumeration, run once and reused; **no extra scan, no vector search, no LLM gate — grep level stays the ceiling**). On a title hit, Read that note — the same lookup update-over-create already requires. Scribe returns **exactly one verdict per item** — closed enum, **4 values, never extended**:

     | Verdict | Meaning | Effect |
     |---|---|---|
     | `promote` | new knowledge, or adds nuance to an existing note | write — create, or update-over-create (Step 2) |
     | `already_known` | an existing note already covers it; nothing to add | reject-log line, this code |
     | `not_durable` | despite the score, one-off/session-bound — fails the 3-month test | reject-log line, this code |
     | `unsupported` | claim without evidence (guess/unverified — the conf=0 signature) | reject-log line, this code |

   - **Dedup discipline is unchanged**: keep capture cheap; deep dedup and junk cleanup stay Dreaming's (batch) job ("do not force perfect dedup — write roughly, Dreaming cleans up", `docs/knowledge-escalate-convention.md`). When torn between `promote` and `already_known`, choose `promote` (the update path) — `already_known` is only for items with **literally nothing to add**. Gate 2 trims obvious re-learnings; it does not buy perfect dedup.
   > **Destination by scope** (layer canon: `docs/vault-tree.md` §Tree axes · promotion topology: `docs/knowledge-escalate-convention.md`): a project-scoped `promote` goes to `<project>/knowledge/` as before. A **cross-project** item splits on Gate 1 — **gate pass → the common layer directly** (its topical folder; sub-axes are topic-free, only `*policies*` names are normative — and those stay behind the signature gate below) · **gate fail + cross-project value → a full note in `<vault-root>/candidates/`** (root-fixed promotion-candidate pool; later promotion = **one file move** into the common layer, no rewrite). `candidates/` is **excluded from recall by design** (unvalidated candidates must not prime sessions — `skills/_session-shared/recall.md`), so parking there costs nothing until the note earns its move.
   > 🔴 **Sole exception — `common/policies/` is never written automatically** (canon: `docs/knowledge-escalate-convention.md` §common/policies). An item that reads as **obligation** (binds every project — a must; origin-agnostic, be it an external mandate like a law·regulation·certification or a self-imposed org-wide invariant) is promoted on its normal tier as usual **and additionally returned as a `common-policy candidate`**; the calling skill collects them and presents **one batch** for the user's signature (`skills/sh`·`sc`). **Agents draft; the user signs.** Everything else stays automatic — the two-gate judgment is unchanged.

2. **Delegate to the scribe worker** — spawn a subagent with the `Agent` tool and hand it a **recording brief** (`scribe` = a worker given a recording brief — a label, not a resident agent; `docs/memory-control-convention.md`). What goes into the brief:
   - **Context**: `vault-root` (the value defined in the project `CLAUDE.local.md` — recorded by `/brain:init` onboarding. No hardcoding) · `project` · session `uid` · the current local datetime (`YYYY-MM-DDTHH:MM:SS` — what `updated:` stamps take; the reject-log line keeps its date-only `<YYYY-MM-DD>` format).
   - **Every `Learned` item** (verbatim — no compression, no paraphrase. scribe = verbatim scribe). scribe judges via the **two-gate judgment (Step 1)** — write only `promote` verdicts, reject-log the rest with their reason code.
   - **Scope instruction**: "perform the knowledge promotion" — the scope this procedure requires is promotion. Session Progress, park/closing entries, and frontmatter are **also written by scribe** — the calling skill passes that content in its own recording brief (it may be merged into this promotion brief or be a separate scribe worker — the calling skill's document decides. But if the same file is touched, **merge into one worker** — only the PM can see the overlap).
   - **Glossary anchoring — existing note titles (guards `related:` against silent forks)**: attach the **project `[K]` + common `[C]` title list** that recall's grep priming already emits (`skills/_session-shared/recall.md` §grep priming — the `[K]`/`[C]` `find | grep '^title:'` enumeration). **Reuse that grep priming — build no separate glossary scan** (cost stays 0). Instruction to scribe: **the new note's `title`, body, and every `related:` target must reuse a title from this list verbatim** — only natural case correction is allowed; no paraphrase, abbreviation, or rename of an existing entry. Coin a new term **only after confirming it is absent from the list**. Rationale: brain leans on explicit `related:` links for multi-hop recall (`docs/knowledge-convention.md`), so one concept spelled three ways (`Cloudflare Tunnel`/`cf tunnel`/`CF Tunnel`) silently splits the graph. **The list + this instruction is the whole mechanism — no fuzzy matching, uuid, or normalization layer.**
   - Have scribe write each item **whose verdict is `promote`** in `docs/knowledge-convention.md` format (trigger-first atomic note) to its **Step-1 destination** (project-scoped → `<vault-root>/<project>/knowledge/` · cross-project gate-pass → the common layer's topical folder, never a `*policies*` directory · below-bar cross-value → `<vault-root>/candidates/`), **update-over-create** (if a similar note exists, find it via grep and update — v1 grep; **update with `Edit`, never `Write`** — `Write` on an existing note discards whatever a concurrent session put there, while `Edit`'s `old_string` is a compare-and-swap that fails loudly instead. `Write` is only for a note that does not exist yet), append one line to the **destination folder's** folder TOC — `_index.md`; where only a legacy `index.md` exists, append there instead (folder-TOC equivalence: `docs/vault-tree.md`) — and add the session uid backlink to `source_sessions` (vertical), **the verbatim source line(s) to `source_items`** (item-level provenance — the brief already carries every Learned item verbatim, so this is a copy, not a rewrite; on update-over-create append, never rewrite existing entries — canon: `docs/knowledge-convention.md` §Item-level provenance), plus `related` lateral links to adjacent knowledge.
   - **Obligation test (the basis for the return below)**: mark any item that **binds every project in this vault (a must)** — as opposed to advice·preference·technique (should/can) — as a `common-policy candidate`. The test is binding force + scope, **not origin**: an external mandate (law·regulation·certification) and a self-imposed org-wide invariant both qualify. Independent of the two-gate judgment: the item is still promoted or reject-logged as usual, and the mark is purely additive.
   - **Rejected items** (Gate-1 below-bar **without cross-project value** — the cross-value ones parked in `candidates/` instead — plus Gate-2 `already_known`·`not_durable`·`unsupported`) get one line appended to `<vault-root>/<project>/knowledge/0.rejected.md` — **reject-log format (canonical = this document)**: `- <YYYY-MM-DD> · reuse/prevent/conf=a/b/c(=sum) · <reason> · "<verbatim Learned>" · <session uid>`. `<reason>` = the Gate-2 verdict; a Gate-1 below-bar line always carries `not_durable` (its real rationale is the score triple — `sum < 3` on the line tells the gates apart). Plain uid, **no `[[ ]]`** — the log lives on the team-shared surface while a session may sit outside it (a shared vault gitignores sessions/; per-vault choice — versioning-convention §Share scope), so a session wikilink would dangle. The log has no `title:`, so recall (title grep) does not pick it up. **Dreaming re-reads this log under the third-time test** — the same item logged **≥2 times** becomes a re-promotion proposal, so a below-bar item is deferred, not dead — **and additionally tallies the `<reason>` codes** (recurring `already_known` = a recall-defect signal). **Canon for those scans is `skills/dreaming/SKILL.md` §3 — do not infer their rules or scope from this line.**
   - **scribe returns**: the list of `→ promoted: [[Note Title]]` backlinks for created/updated notes + **every vault path it wrote** (notes · `_index.md` · `0.rejected.md`) — the calling skill stages exactly those and nothing else — + reject count **per `<reason>` code** + **`common-policy candidates`** (the items marked by the obligation test — verbatim text + the note they landed in; **scribe writes nothing to the vault common layer's `policies/`** (`BRAIN_COMMON/policies` — `.brain-paths`, resolved by `scripts/vault-paths.sh`)).

3. **Replace, do not duplicate** — put the backlinks scribe returned onto the session's corresponding `Learned` lines: `→ promoted: [[Note Title]]`. **This replacement is also a session-file write → delegate to scribe** (the PM writes no vault content — "Write boundary" above). The PM only briefs "which backlink goes onto which `Learned` line". Never copy knowledge note bodies into the session.

4. **Policy signature batch (only when `common-policy candidates` came back)** — the PM presents the **whole list at once**, **immediately after the promotion delegation returns** (AskUserQuestion suits it; the calling skill may already have folded Step 3 into a later delegation, so do not tie this to a step number). **Per-item interrupts are forbidden** — one batch per promotion point, or none at all. Approved items go to a **follow-up scribe brief** writing them to the vault common layer's `policies/` — `BRAIN_COMMON/policies`, where `scripts/vault-paths.sh` resolves `BRAIN_COMMON` from the vault's `.brain-paths`; never a literal path — (`docs/knowledge-convention.md` format + one line in that folder's `_index.md` — legacy `index.md` equal, vault-tree.md); unapproved ones **stay as project knowledge — nothing is discarded and nothing is re-asked**. With no candidates, this step produces no prompt.

## Forbidden

- **No CLI writes** — every promotion write goes through the `Write`/`Edit` tools (canon: `vault-io.md` §1, alongside this file). And pointing that write at vault content happens **only inside a scribe worker's brief** — the PM (main session) does not write directly even though it has the tool (single-scribe discipline, "Write boundary" above). Do not bypass; delegate.
- Never record secret values in plaintext.
- The old claude-obsidian procedures (`/save`·`allocate-address.sh`·`legacy-pages.txt`·`concepts/meta/entities`·`log.md`·`hot.md`) are **not used** — in the new vault graphify is the read index (`README.md` §Architecture); no need to reinvent hand-rolled index/log. Only the one-line folder `_index.md` append.
